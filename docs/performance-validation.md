## 新增的宿主 GPU 正式验收门槛

新阶段 A/B/C 的正式性能结论，必须记录 App 选定的 renderer/backend、实际 worker PID、加载的 ICD / Vulkan loader / Mesa 与 Turnip 库的终态映射及 SHA256、枚举并实际创建队列的 physical device 名称/ID、guest GL 绘制、host EGL/Vulkan 提交、同步 readback、DELT 回写、IOSurface 复用上传、App ring/screendump 取帧、最终显示变化的端到端证据。仅见到 worker 进程、装有 Vulkan 包或 draw 命令，不能证明物理 GPU 执行；需确认实际获胜 physical device/队列并有可关联的 submit/fence/readback 数据。具体采集字段由 transport/lead 对齐当前 GL worker 架构。

App 0.31.8 的 Adreno 静态准备错误会持久化切到 OSMesa。若本轮发生自动/手动 fallback，则设备界面可用或 guest 内容发生变化均不能通过“Adreno/VKGL 真实宿主 GPU”门槛。验收要报告保存的偏好、实际 backend、QEMU/worker 进程映射及 Vulkan ICD/physical device；源 QEMU software GL/swrast、host Zink/Turnip VK 和 Android App screendump 是三个不同位置，不可统称“GPU 回退”。App screendump 只是在帧环失效时另一条 capture 路径，不能推断 guest 从 Adreno 切成软件光栅化；反之 ring 工作也不能证明使用 VKGL。静态启动失败回退到 OSMesa 应归为兼容/可用性成功、Adreno 性能目标失败。

阶段 C “典型交互持续 ≥5 FPS、评估 10 FPS”应对上述真实 Vulkan backend 全链端到端的 visible-content rate 验收。Ring publications、guest readback、QEMU 本地 screendump 间隔都只能作子路径诊断，不作为此目标的分子。正式验收需同一 run 同时留有效 backend/physical device 证据与前述两类连续内容证据，任何一项缺失即标未知/未通过而不是估算通过。

## Readback source and final-panel identity

The HFR2 ring is a GL IOSurface-readback tap, not a MiniFB final-panel feed. Redwood `frame_end` iterates all drawn targets and sends each through readback; the worker publishes each successful `EA_READ` based on dimensions before the guest applies the reply to its IOSurface. MiniFB later chooses/queues layers at `SwapEnd`, composes multiple source/destination layers into `fBase` on `show`, and may write boot-log overlay or settle output afterward. Ring metadata does not identify target/FBO, SwapID, or final panel; D1 opaque tokens identify private delta bases only. Thus the ring cannot establish scanout identity even when one sampled Settings screen happens to match a final RAMFB snapshot. The current App default disables the raw tap and retains canonical full-resolution PPM capture; ring is diagnostic, not the FPS source.

A missing rectangle found in a ring frame is not by itself a driver diagnosis. Pair one readback's request sequence, context, target/FBO/attachment, key and ring sequence with the guest frame_end target and subsequent MiniFB SwapID, layer source IDs and source/destination rectangles. Then capture final `fBase` after the chosen completed composition, overlay and settle boundary, with writer exclusion/coherence. If the target readback is already missing pixels, inspect its clear/viewport/scissor/attachment/upload; if the target is correct but final panel is not, inspect layer selection/composition; if final panel is correct but App output is not, inspect guest writeback, App capture source, bitmap ownership and UI presentation. Free-running screendumps between writers must be labeled unpaired. A reported pair matching every pixel in a particular final Settings capture establishes only that state, not a general equivalence between ring targets and final display.

The D123-r3 paired audit [`d123-r3-frame-stage-v1/result.json`](../../hackios-run/lead-render-audit/d123-r3-frame-stage-v1/result.json) records two stable guarded ring-publication brackets (seq 259 and the following pair) that each matched all 2,740,500 RGB pixels of the final RAMFB snapshot. The captured UI was a Settings list, not Home; the Home-gesture return was not demonstrated, and the pre-interaction comparison was not bracketed. This validates those specific paired final Settings states only. It does not identify the ring source as scanout for all surfaces or states, nor restore the App's raw-ring default.


The PPM comparison tool must honor the source header, maxval, orientation and verified row pitch. The captured 1125-pixel PPM body uses 3376 bytes per row (3375 RGB bytes plus one padding byte); treating it as packed 3375-byte rows shifts later lines. Strip this pad only after validating payload size/layout; do not relax the ROI threshold or hide producer-side black rectangles to compensate for a decoder error. Keep producer BGRA, PPM RGB and PNG reference comparisons separate.

## App bitmap/presentation boundary

Static App inspection found that `CapturePipeline` reuses one mutable `Bitmap` and calls `setPixels` on the capture thread; `DisplayScreen` obtains the same bitmap through `asImageBitmap()` and uses it later in Compose Canvas. HFR2's guard protects the mapped-ring-to-`IntArray` copy, not Bitmap writes versus Skia/RenderThread consumption. The volatile bitmap reference is not evidence of immutable pixel ownership or an Android frame-commit fence. No ART/Compose/SurfaceFlinger presentation test was performed here: this is an unverified concurrency/commit risk, not a confirmed tear bug. Do not add an expensive copy or claim display atomicity without targeted evidence. Final visible FPS needs a stable content/frame identity through producer final panel, App read/copy, UI draw submission and actual presentation/commit.

## Final-frame measurement at 1125×2436

1. Freeze the guest, worker, QEMU and App artifact hashes and record the selected renderer, session ID and capture source. Run the same scripted interaction in each comparison. Start from a verified Home state, capture the Settings transition and return, and include a sustained animation or scroll long enough to measure changing content. Log input timestamps on a monotonic host clock and verify the resulting screen states from pixels.
2. At the completion of MiniFB composition, record a present ID, monotonic timestamp, geometry, stride and format. Include subsequent overlay and settle updates that write the final panel. Read `fBase` with a writer-exclusion or generation protocol and recheck the generation after copying. Use a paired QMP/RAMFB screenshot as a pixel control. If the run has only free-running QMP screenshots, report their sample rate and observed distinct-frame rate as sampled final-buffer metrics.
3. Normalize every coherent captured frame to all 2,740,500 visible RGB pixels. Verify pitch and byte counts, then retain the whole-frame hash, frame ID and timestamp. Verify the interaction and visual integrity with the full images and fixed regions for icons, labels, the Settings list and controls. Compare against a reference at the same UI state and exclude blank areas only where the reference is also blank. Preserve evidence of incomplete regions, unexpected black rectangles, orientation errors and mixed frames.
4. Count transitions between distinct consecutive content frames in each predeclared active interval and divide by the elapsed seconds on the same clock. Report the length of each interval, sampling cadence, duplicates, skipped IDs, and median and p95 intervals between distinct frames. Include a sustained active window and separate startup and input-to-first-visible-change times. A sampler whose cadence or drops cannot resolve 10 FPS leaves that threshold unverified. A gap in the return gesture or invalid visual evidence leaves that scenario unverified even if the aggregate count is high.
5. For App-visible FPS, associate the final-frame ID with App ingestion and draw submission and observe which IDs reach presentation. A frame-commit callback marks submission and needs a matched presentation timestamp or equivalent visual observation for visible FPS. Where Android instrumentation or presentation IDs are unavailable, report the final-framebuffer measurement and mark App-visible FPS as pending. Match GPU queue completion to the same run and relevant draw/readback work when claiming acceleration for the workload.

## HTB1 batching review

The frozen v2 experiment used a Linux C client over a socketpair connected to the Android worker. All nine sampled shader cases had identical RGBA hashes and GL error 0 across the three runs. The new worker took 201 wire requests with batching off and 153 with batching on. The enabled run queued 82 commands and flushed 31 batches. The legacy worker took 202 requests, including a single rejected capability probe, and continued on the same stream. An independent rerun of the frozen v2 CPU client fixture passed. [Native v2 results](../../hackios-run/patched-transport-batch/native-v2/manifest.json)

The worker validates the complete batch before executing child commands. The client owns a deep copy, drains before synchronous wire queries and flush/finish, and poisons the stream after ambiguous I/O or a failed batch. The v2 client samples the per-call clock only for read and texture operations. The guest scalar wrapper drains pending commands before returning a thread-local GL error. A failed drain also prevents rebinding to a new client. The targeted boundary fixture exercised all three cases. HTB1 activation is opt-in. Guest TCP activation receipts and final-frame throughput still require an iOS guest run. [Boundary fixture results](../../hackios-run/patched-transport-batch/native-v2/validation-boundaries-final.json)

## Optional exact IOSurface snapshot candidate (not built into a guest)

Static/native review artifacts are [`redwood-exact-v1/identity.json`](../../hackios-run/patched-guest-load/exact-snapshot/redwood-exact-v1/identity.json) and [`native-v2/result.json`](../../hackios-run/patched-guest-load/exact-snapshot/native-v2/result.json). Native v2 ran all 12 budget × opt × profile combinations with exit 0, including exact-source byte/refill/tail/padding/guard tests, allocator failure, cache eviction/LRU, image rebind/delete/context release and barrier-synchronized two-context ownership tests. It is a tracked host-native allocator fixture with synthetic clocks—not a full SDK link, Mach-O, guest execution, TCG workload, or FPS result. ASan was not achieved because this host could not start its runtime; do not report an ASan pass.

The manager lock protects shared snapshot metadata, owner relocation, allocation/LRU and CPU compare/copy; it does not lock IOSurface writers globally or make a shared surface an atomic snapshot. Pixel-span correctness and source ownership therefore still rely on the existing caller contracts, and foreign CPU writes racing the read can yield a mixed observation. The global mutex also serializes potentially large CPU compare/copy work across contexts; no real startup or frame-time benefit is established. Keep this optimization default-off until a separately hashed full-SDK/guest build is exercised under the target workload and measured against final displayed content.
