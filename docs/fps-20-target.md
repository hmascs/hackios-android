# 「实际 20 FPS」的账本（0.31.2 实测口径）

用户的目标是**画面实际 20 FPS**，即每帧 50 ms。这份文档只做一件事：把实测数据摊开，
说明现在差多少、每一段能省多少、以及 20 FPS 到底需要改什么。**标「实测」的是量过的，
标「推算」的是按实测比例算的，两者不混。**

## 1. 现在到底几帧

| 指标 | 值 | 来源 |
| --- | --- | --- |
| 内容帧率（画面真的变了） | **0.05–0.7 FPS**，典型 0.1–0.3 | 实测：一次 1185 s 的 boot 里 `redwood-gl: frame` 只有 66 帧；驱动自报的 54 个 `N frames in T ms` 样本折算 0.049–0.66 |
| stock 11.1.2 运行时基线（App 现用二进制，前 120 s） | 首帧 **60.5 s**（66.5 / 54.4 两次），QEMU CPU 179.8 s，2 帧 | 实测（`docs/cpu-translation-baseline.md` 的 ABBA） |
| Inferno 10.2.2 运行时（同一次 ABBA） | 首帧 **53.1 s**（55.1 / 51.2 两次），QEMU CPU 173.2 s，2 帧 | 实测，约 **快 12%** |
| 单帧墙钟（来宾自报） | **1.58 s**（60 条完整计时的中位数） | 实测 |
| 其中 `copying out`（回读+传输+写回） | **1.14 s = 72%** | 实测 |
| 其中 `handing on` / `waiting` | 2–4 ms / ~0 ms | 实测 |
| 帧时间内 QEMU CPU 利用率（2 vCPU 上限 2.0 核） | 中位 **1.37 核**，帧间隔内 1.55–1.66 核 | 实测（引导期 logo 阶段；桌面窗口待测） |
| App 采样率 | 17–20 次/秒 | 实测（0.31.2 状态条） |
| QEMU 侧 `screendump` 写 8 MB PPM | **30.0 ms**（HMP 往返）/ **41.1 ms**（完全落盘），10 样本 | 实测；同目录 `dd` 945 MB/s，文件系统不是瓶颈 |
| 目标 | 20 FPS = 50 ms/帧 | 用户要求 |

**1.58 s ÷ 50 ms = 31.6× 的差距。** 采样 18 次/秒不代表画面 18 帧/秒——0.31.2 起这两个数
分开显示（`docs/capture-metrics-0.31.2.md`）。

## 2. 一帧要走的四段路

```
① 来宾 TCG 跑 CoreAnimation/Redwood 合成        0.44 s（= 1.58 − 1.14，推算；CPU 1.55 核 → 确实在跑 TCG）
② glReadPixels(1125×2436) + SLIRP TCP 送回来宾   1.14 s（实测 72%）
   —— 其中宿主 glReadPixels 只 15 ms，其余 ~1.53 s 全是传输（实测，见 §3.5）
③ 来宾把画面写进 QEMU framebuffer                （未单独量，含在 ①）
④ 宿主 App：HMP screendump 写 8.2 MB PPM + 读回 + 解码   QEMU 侧 30–41 ms + App 侧 40–56 ms
```

④ 的真实量级：QEMU 侧 30–41 ms + App 侧 40–56 ms ≈ **56 ms/帧**，即 App 取帧上限 ≈17.8 样本/秒。
一度算成 250 ms 的那版是错的——QMP 的 `screendump` 异步返回，命令返回时文件还没写完，
量到的是半截 1.4 MB 文件再按字节线性外推；改成同步 HMP + 等文件稳定后实测就是上表的值。

结论：④ 只差 6 ms 就够 20 FPS 的 50 ms 预算，**真正的墙在 ①（来宾 0.44 s）和 ②（回读 1.14 s）**。

②是最大的一块，也是唯一「明显有 10× 空间」的一块：10.96 MB / 1.14 s = **9.6 MB/s**，
这个速度不像内存带宽（几 GB/s），更像「SLIRP 里每字节都要经过来宾 TCP 校验和 + 两次拷贝」
的量级——但**这是推断，没做过三段拆分**（worker 日志里没有耗时字段，要重编 worker 才有）。

## 3. 逐段能省多少（按实测比例推算）

> **本节的「②」一行已被 §3.5 的实测取代**：② 里真正贵的是传输（1.53 s），不是回读（15 ms），
> 也不是逐像素换字节（47.6 ms）。先读 §3.5 再看这张表。

| 手段 | 效果 | 结论 |
| --- | --- | --- |
| 去掉 ②（零拷贝回读） | 1.58 s → 0.44 s ≈ **2.3 FPS** | 实测比例推算，仍差 8.8× |
| ② 减字节：RGB565 或脏矩形（10.9 MB → ~1.4 MB） | ②1.14 s → ~0.15 s，总 ~0.6 s ≈ 1.7 FPS | 推算 |
| ② 换传输（virtio-serial / vsock / 共享内存环，省 TCP 校验和与两次拷贝） | 1.14 s → 0.2–0.3 s（乐观） | 未实测，要重编 worker + 改来宾侧 dylib |
| ① 来宾 CPU 提速（TCG 编译选项、vCPU 数） | 0.44 s 部分受益，个位数到十几个百分点 | 部分实测（见 `docs/cpu-translation-baseline.md`） |
| 编译配置 `--disable-debug`（去掉 `-DDEBUG -fno-omit-frame-pointer`） | 待 AB，方向明确 | 0.31.3 计划 |

即便把 ② 压到接近 0，剩下的 0.44 s 也要再砍 **8.8×**。**所以 20 FPS 不是「把某一条链路优化掉」
就能到的，必须让来宾侧的合成/光栅化也不再在 TCG 里跑。**

## 3.5 实测拆分：copy-out 的 1.5 s 是**传输**，不是逐像素换字节

这一节替换掉先前「copy-out 主要是逐像素 swap 循环」的推断。**推断错了**，实测如下。

二进制：`/tmp/eagl-b1/libredwood-gl.dylib`（从当前 `userland/src/eagl.c` 用
`qemu/gpu/build-redwood-remote.sh` 在机上重编，未改源码的产物与 App 内装的那份
**sha256 完全相同**：`4e9221a7…`，558 704 B，402 个导出符号全同 ⇒ 工具链可复现）+
`glpass-worker.b1/hackios-zink-session`（NDK 重编，带宿主计时）。来宾自报
`hackios-gl: out N …` 与宿主 `EAGL readback timing` 同一帧对得上：

| 段 | 第 1 帧 | 第 2 帧 |
| --- | --- | --- |
| 宿主 `glReadPixels`（GL→宿主内存） | 15.7 ms | 14.0 ms |
| 宿主 `write()` 把 10.9 MB 压进 chardev | **1.535 s** | **1.669 s** |
| 来宾 `read()` 收 10.9 MB | **1.569 s** | 1.704 s |
| 来宾 `malloc` 10.9 MB | 0.34 ms | 1.1 ms |
| 来宾逐字节 swap 解包（现状） | **47.6 ms** | — |
| 来宾 32 位字 swap 解包（C1） | — | **35.8 ms** |
| 合计 copy-out | 1.65 s | 1.77 s |

结论（实测）：**逐像素换字节只占 2.9%，字数化只省 12 ms（0.7%）。C1/A2 两条优化作废。**
宿主写和来宾读两边都 ~1.55 s，说明瓶颈在中间那段管道本身，而不是任一端的 CPU：

```
worker --write--> [unix socket chardev] --QEMU slirp--> virtio-net --> 来宾内核 TCP --> 来宾 read()
                                                          ~7 000 个 1500 B 包，每个包都要在 TCG 里
                                                          跑一遍来宾内核网络栈
```

10.96 MB ÷ 1.55 s = **7.1 MB/s**。这个数跟「带宽」无关，跟**包数**有关：约 7 000 个包 /
1.55 s ≈ 220 µs 一个包，正是 TCG 下来宾内核处理一个 virtio-net 包（中断 + skb + 校验和 +
拷贝 + ACK）的量级。**所以任何「少几个字节」「少几条指令」的优化都动不了它**，只能减少
跨越这道边界的次数。上行（`pack` 后送进路由器）更差：启动时 `send=3.28 s`，这也是 attach
那 2.4 s 的主因。

### 为什么不能「让宿主直接写来宾 RAM」

App 给来宾 RAM 的参数是 `-object memory-backend-file,…,readonly=on,rom=off,share=off`：
`share=off` ⇒ QEMU 用 `MAP_PRIVATE`，**外部进程写 RAM 文件来宾看不到**；`readonly=on` ⇒ 文件
以只读打开、来宾的写走 CoW（这正是不污染底层镜像的设计）。所以宿主 worker 无法 mmap 到来宾
RAM。**能碰来宾 RAM 的只有 QEMU 自己**（`address_space_write` / `address_space_map`）。

### 正确的修法：让 QEMU 搬，或者干脆不搬

已实测的 QEMU 侧速度（同一台机器，`qemu-system-aarch64` 8.2 + QMP `pmemsave`，
10.9 MB，3 次）：**55 ms 冷 / 41 ms 热**。即 QEMU 自己搬一次 10.9 MB 约 **40–55 ms**，
比走 TCP 的 1 550 ms 快 **30 倍**。由此外推：写入来宾 RAM 是纯 memcpy，约 10–15 ms（推断）。

按此，三条路按性价比排序：

| 路线 | 做法 | 预期 | 量级 |
| --- | --- | --- | --- |
| **A6 帧环（首选）** | worker 渲染完**不送回来宾**，直接交给 App 显示；来宾的 `read_surface` 变成空操作 | copy-out 1.32 s → **0** | 每帧都付，**主战场** |
| P3 像素汇 | 在 QEMU 里加一条 bulk 通道（host⇄guest RAM），替 worker 搬 | 1.55 s → 0.04 s | 同上，但要多写 QEMU 代码 |
| 上行（次要） | 只有 **4/41 帧**付全尺寸重传（10 885 KB，代价 2.05 s），其余 37 帧为 0 | 收益 ≈ 总时间的 10% | 先不动 |

A6 的前提是一个待验的事：**把 `hios_eagl_read_surface` 改成空操作后，来宾画面是否照常推进**
（若 CA/WindowServer 后续还要读回这块内存做脏矩形/一致性判断，空操作会让画面停住）。这一步
（P2）由子代理在机上验，通过才做 A6；不通过就必须走 P3 把像素写回来宾 panel。

### A6 实测（同一次启动内 A/B，决定性）

`glpass-b2`：前 60 次读回让来宾收像素（v0），第 61 次起带 `NO_REPLY`。桌面窗口 n=136
（36 帧 A + 100 帧 B）。**同一启动内比值才可信**——这轮机器偏慢（同一份 10.9 MB 的 copy-out，
b1 是 1.57 s、这轮 5.38 s；串口有 lsd 刷屏、温度 60–74 ℃），绝对值偏悲观。

| | A：来宾收像素 | B：跳过（NO_REPLY） |
| --- | ---: | ---: |
| 来宾这次读回总耗时 | 2 375 148 µs | **43 486 µs** |
| ├ 收 10.9 MB（body） | 2 271 390 | 14 |
| ├ 等回复头（宿主 readback+转换+写环） | 20 910 | 42 331 |
| └ 解包 | 61 897 | 0 |
| 帧间空闲 gap | 484 862 | 710 092 |
| **单帧周期（读回 + gap）** | **2.86 s（0.35 FPS）** | **0.754 s（1.33 FPS）** |
| eagl.c 自报 copying out | ~2.3 s | 77–96 ms |
| 内核 IOMFB 驱动内耗时 | — | 9.8–10.3 ms/帧 |
| 环 seq | 不发布 | 0→100，与帧 1:1 |

**P2 成立**：跳过之后单帧 2.86 → 0.754 s（3.8×），环 seq 持续增长，环里是**完整正确的
SpringBoard 主屏**（1125×2436，图标/时钟/Dock 全在）。所以「CA 不需要读回那块像素」这个前提
是实测成立的，A6 这条路走得通。

### B 段那 754 ms 的成分（实测 + 相减）

- **43 ms** = 我们这条读回路径（宿主 glReadPixels 16 + BGRA 转换 9 + 环拷贝 ~4 + 往返）；
- **35–55 ms** = 读回周围那几次 GL 往返（77–96 − 43）；
- **~10 ms** = 来宾内核把整屏拷进 panel（swap 日志 `from 0,0 1125x2436 to 0,0 1125x2436`，
  与 TCG 下 10.9 MB memcpy 的 ~1.1 GB/s 相符）——**这部分与像素面积相关**；
- **~650 ms** = 来宾自己在 TCG 里跑 SpringBoard/CA：场景构建、XPC、CA 提交、CG 光栅化、
  纹理上传（每帧 22–67 次 GL 调用 / 2–9 次 draw）。**其中有多少与像素面积相关，还没测**
  ——见下一节，这条不能想当然。

### 于是唯一还剩的杠杆

那 ~700 ms **不是**命令往返。直接从 b2 的 `serial.log` 统计 92 条 `redwood-gl: frame`：

| 段 | 帧数 | total | handing on（一帧所有 GL 命令） | wait | copy-out | 残差 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A（来宾收像素） | 88 | 2424 ms | **3.5 ms** | 0.01 ms | 1773 ms | 619 ms |
| B（NO_REPLY） | 4 | 783 ms | **5.7 ms** | 0.01 ms | 78 ms | 700 ms |

一帧 53–61 次 GL 调用，**全部命令往返加起来只有 3.5–5.7 ms**（单次约 0.09 ms）。所以
「每次调用一来一回吃掉 10 ms × 22–67 次 = 650 ms」这个推断是**错的**，命令批处理那条优化作废
（最多值个位数毫秒）。

真正的两份成本很清楚：**copy-out（1773 → 78 ms，A6 已经拿走）** 和 **残差 619–700 ms
（A6 前后一样，说明它与我们的通道无关，是来宾自己的帧工作）**。

残差里有多少与像素面积相关，还没测。**不能凭「CA/SpringBoard 是逻辑开销」想当然**——SpringBoard
这一帧要 CoreGraphics 光栅化整个主屏（图标、文字、可能的模糊）并按面积上传纹理，这些**本来就是
面积相关**的。所以降倍率（`fbscale` 3→2→1）仍然是唯一还没被证否的乘数，判据是
`残差(fbscale=1) / 残差(fbscale=3)`：掉到 0.4 以下就值得做，几乎不动就彻底放弃。

### 一个重要的量级警告：跨启动漂移 3.4×

同一份 10.9 MB 的回写，`glpass-b1` 是 1.57 s、`glpass-b2` 是 5.38 s（**3.4×**），b2 那轮串口有
lsd 刷屏、温度 60–74 ℃。所以下面所有绝对毫秒都必须带上「哪一轮」才成立，**A/B 只在同一次启动内
可比**。这也意味着 700 ms 的残差同样可能被机器状态放大/缩小 3.4 倍：健康状态下它可能是
200–300 ms，那时「零跨界」方案的帧时间就是 0.2–0.3 s ⇒ **3–5 FPS**。

所以天花板不是一个数：
- 慢机器状态（b2）：零跨界 ~0.75 s ⇒ 1.4 FPS；差分回写（变化 20%）~1.05 s ⇒ 0.95 FPS；
- 健康状态（b1 量级）：零跨界 ~0.25 s ⇒ 4 FPS；差分 ~0.35 s ⇒ 2.9 FPS。

**结论：能否进 2–5 FPS，取决于机器状态，而只有「零跨界」那条路在健康状态下能进去。**
这也解释了为什么用户实测「只快了一点点」：0.31.4 的 754 ms 是在 b2 那种慢状态下测的。

### 传输这条路已经没有别的余地

`net/slirp.c` 里**没有 `vnet_hdr`/GSO 支持**（grep 无命中），所以 virtio-net 永远是 MTU 1500、
每 10.9 MB 约 7000 段、~213 µs/段。**减少每字节的成本做不到，只能减少字节数或干脆不传。**

### 因此天花板（用实测替换先前推算）

- A6 已实测拿到的那部分：**copy-out 1773 → 78 ms**，单帧 2424 → 783 ms，**3.1×**；
- 落在哪一档取决于残差里面积相关的比例（这一轮的机器偏慢：同一份 10.9 MB 的 copy-out，
  b1 是 1.57 s、这轮 5.38 s，所以 700 ms 的残差本身也可能被串口刷屏/热拖大）：
  - 若降倍率后残差掉到 ~0.4 倍 ⇒ 单帧 ~350 ms ⇒ **2.8 FPS**；
  - 若几乎不动 ⇒ 单帧 ~700 ms ⇒ **1.4 FPS**（快机器上推 ~2 FPS）；
- 再往上就只剩「让来宾别在 TCG 里跑合成」——本机没有 `/dev/kvm`，没有可用乘数。

所以对用户「2–5 FPS」的目标：**下限 2 FPS 有把握，上限 3 FPS 取决于降倍率实测**；
5 FPS 在当前架构下没有路径。最终数字以真机为准。


## 4. 2026-11-19：一次走错的路，和它留下的两条真结论

### 4.1 先修一个测量错误：payload 里的内核不是 App 里的那份

`glpass-desktop.py` 的 payload 是外部传进去的。一直在用的
`redwood-settings-content.M5VER6/boot/payload.bin` 嵌的是 **16 809 112 B** 的内核
（`__TEXT_EXEC` @ `0xfffffff007294000`），而 App 从 assets 装的是
`mach.development.bcm2837`，**15 791 240 B**（`__TEXT_EXEC` @ `0xfffffff00728c000`）。
拿仓库里的内核去符号化那些 PC，得到的是「49.9% 在 `_pmap_test`」这种不可能的结论
（`pmap_test` 在 `#if CONFIG_XNUPOST` 里，串口只有 "No POST boot-arg set."，它根本没跑）。

现在用 `payload-shipped.bin`（内核 = assets 里的那份）重建 payload，符号化才有意义。

### 4.2 PC 采样在这个来宾上是**有偏的**，不要用它下结论

换成正确的内核之后，`--pc-sample` 给出的分布是：

| 函数 | 占比 |
|---|---|
| `_ml_get_timebase` | 35.3% |
| `_ml_get_speculative_timebase` | 11.7% |
| 用户态 | 33.2% |

看起来「一半的来宾 CPU 在读时间戳计数器」。于是做了两件事：给 QEMU 打补丁让读计数器不结束
TB（`qemu/patches/0002-*`），再把计数器改成用宿主 `cntvct_el0` 精确换算
（`0003-*`）。然后**直接在 QEMU 里数**：每 30 s 打印这段代码被调用了多少次、每次多久。

实测（同一次启动，交替统计）：

```
hios-ab: mode=stock  calls=1051370  ns_per_call=104.2     # 35k 次/秒
hios-ab: mode=scaled calls=1455718  ns_per_call=104.2     # 48k 次/秒
```

**35k–48k 次/秒 × ~100 ns ≈ 每秒钟 4 ms，即 0.25% 的一颗核。** 不是 47%。

偏差来自 QEMU 自己：`ARM_CP_IO` 寄存器访问前会 `gen_a64_update_pc()` 把**这条指令的地址**
写进 `env->pc`，而 `info registers` 读的就是 `env->pc`；于是采样点会堆在这条 `mrs` 上，
看起来像热点。**这个来宾上 PC 采样不可信，只有「数次数」和「计时」才可信。**

### 4.3 那 540 ms → 382 ms 是怎么来的？大概率是跨启动漂移

同一套配置（同镜像、同 dylib、同 worker）连跑几次，稳态单帧：

| 运行 | 稳态单帧 | 每帧纹理重填 |
|---|---|---|
| 旧 payload + 原版 QEMU | 540 ms | 0 |
| 新 payload + 补丁①② | **382 ms** | 0 |
| 新 payload + 补丁② | 744 ms | 1.15 次 / 788 KB |
| 新 payload + 补丁② | 954 ms | 1.08 次 / 419 KB |

后两次的「每帧纹理重填」不为零，说明**来宾干的活不一样**（SpringBoard 还在做动画/壁纸重绘），
不是同一份工作量。所以 382 ms 那次很可能是碰巧碰上了一个「安静」的桌面。
补丁①②本身是合理的微优化（去掉每秒 3.5 万次多余的 TB 退出），但**不能证明 42%**。

### 4.4 于是得到两条规矩

1. **只信同一次启动内的 A/B**：跨启动可以差 1.9×，比任何待测优化的效果都大。
   要做同启动 A/B，就得让改动可以运行期切换（QEMU 侧一个全局 + `tb_flush`，
   并且把切换时刻用**来宾计数器**同时写进 qemu.log 和 serial.log 才能对齐）。
2. **先对齐工作量再比帧率**：`frame-stats.py` 会把每帧 GL 调用数、三角形数、纹理重填量一起
   打出来；重填量不同的两次运行不能直接比。

`qemu/patches/0002-*`（读计数器不再结束 TB）和 `0003-*`（用宿主计数器换算来宾计数器）
都是**正确性问题之外的纯优化**，留着没有坏处，但**不要再把它们当成 2–5 FPS 的答案**。
