# 渲染倍率：把来宾的像素面积降下来（2–5 FPS 的第二刀）

目标已从 20 FPS 改为**实际内容帧率 2–5 FPS**（用户 2026-11-19 拍板）。20 FPS 不可达的实测依据
在 `docs/fps-20-target.md` §3.5/§4。这份文档只讲第二刀：渲染倍率。

## 为什么是它

A6 帧环（worker 渲染完直接把帧交给 App，来宾不再收像素）已经实测消掉 copy-out
（1773 → 78 ms，单帧 2424 → 783 ms）。剩下的 **619–700 ms 残差**与我们的通道无关，
是来宾自己在 TCG 里跑这一帧。**这份残差里有多少与像素面积相关，目前是未测的推断**：

- 面积相关的候选：CoreGraphics 光栅化整屏（图标、文字、模糊）、按面积上传纹理、
  内核把整屏拷进 panel（实测 ~10 ms）；
- 面积无关的候选：XPC、层树求值、CA 提交、命令往返（实测全部命令只占 3.5–5.7 ms）。

所以降倍率**既没有被证明有用，也没有被证否**。判据只有一个：
`残差(fbscale=1) / 残差(fbscale=3)`——掉到 0.4 以下就值得做，几乎不动就彻底放弃。
（先前两处内部判断都下得太早：一次说「1/9 面积就 1/9 成本」，一次说「几乎无关」，
两次都是推断当结论，这里改成待测。）

## 两个数必须一致

来宾的帧缓冲尺寸由两处决定，**不一致就黑屏**（2026-11-04 实测：WindowServer 按 375×812 建图、
ramfb 是 1125×2436，屏幕全黑而串口里一切"正常"）：

| 决定什么 | 在哪 | 当前值 |
| --- | --- | --- |
| WindowServer 建多大的图 | payload cmdline 的 `fbscale=N` | `Constants.SCREEN_SCALE`（3） |
| ramfb 给来宾多大的帧缓冲 | `loader.efi` 通过 fw_cfg `etc/ramfb` 写入 | loader 里**编死** 1125×2436 |

| `SCREEN_SCALE` | 像素尺寸 | 面积 |
| --- | --- | --- |
| 3（现状） | 1125×2436 | 1.0 |
| 2 | 750×1624 | 4/9 |
| 1 | 375×812 | 1/9 |

App 侧已经收口到 `Constants.SCREEN_SCALE`：`SCREEN_W/H = 375×scale / 812×scale`，
`fbscale` 由它生成，取帧尺寸、点按坐标映射、帧环建尺寸都跟着它走。**默认仍是 3，
与已发布的 0.31.3 行为完全一致。**

## 还没解决的一件事：loader 里的 ramfb 尺寸

`loader.efi` 的 ramfb 尺寸是编译期常量（源码 `xnuloader/loader.c` 的 `PHONE_POINT_*`），
所以严格自洽地降到 2/1 需要改 loader。但**A6 之后 App 看的是帧环、不看 ramfb**，
所以有一种更省的可能：ramfb 保持 1125×2436 不动，只把 `fbscale` 降下来，只要来宾
自己不停手（它的 panel 路径写进一个更大的 ramfb 里，没人再读那块内存）。

这一条由实测判定，判据三条同时成立才算通过：

1. 帧环的 `seq` 继续增长（来宾仍在正常出帧）；
2. 帧环头里的 `width/height` 真的变成 750×1624 / 375×812（不是仍按 1125 建图再缩放）；
3. 单元帧时间按面积比例下降。

通过 ⇒ 不碰 loader；不通过 ⇒ 再去改 loader 的 ramfb 尺寸（`loader.efi` 里那三个常量是
`movz` 立即数，可以用 App 部署时改写的方式做成运行期可配，不必为每个倍率编一份）。

**注意**：App 侧帧环按 `SCREEN_W/H` 建，worker 侧按自己的渲染尺寸校验，不符会**静默降级**
（退回 screendump）。所以测倍率时如果看到"没出帧"，先确认不是这个静默降级造成的假象。

## 与已交付版本的关系

- `SCREEN_SCALE = 3` 时，App 的启动参数、取帧尺寸、点按映射与 0.31.3 逐字节相同，无行为变化。
- 改这个常量只影响：payload 的 `fbscale` 值、`SCREEN_W/H` 派生的所有尺寸。改完 payload 会自动
  重建（`QemuPreflight.needsPayload` 把 boot args 纳入脏标记）。
